## 1. 配置层（`config.py` 新增）

加了三组配置，全部可被 `.env` 覆盖：

```python
EMBED_DIM = 1024            # BGE-large-zh 的向量维度
QDRANT_PATH = "./qdrant_db" # 本地落盘目录（开发期）
QDRANT_URL = None           # 设了就连服务器（部署期）
QDRANT_COLLECTION = "medical_kb"  # 集合名（类似数据库的"表"）

CHUNK_OVERLAP = 80          # 相邻切块的重叠字数
```

**关键设计**：Qdrant 同一套代码，开发用本地落盘（`path=`，无需 Docker），
部署只要设个 `QDRANT_URL` 就切到服务器——这就是为什么 Docker 没装也能先跑。

## 3. 灌库管道（`ingest.py` 新建）——P0 的核心

完整的 **ingestion 五步**，对应 JD 的"RAG 流程"：

```
① 读取    medical_book_zh.json（JSONL，8475 条医学教材段）
② 切块    每段用 RecursiveCharacterTextSplitter 重切到 ≤400 字
③ 嵌入    BGE 把每个 chunk 转成 1024 维向量（每批 64 个）
④ 入库    打包成 Qdrant 的 Point（向量 + 原文 + 元数据）写进集合
⑤ 计数    报告写入了多少
```

**② 为什么要重切**（核心知识点）：原始教材按 2048 字一段，但 **BGE 的输入上限是
512 token**（中文约 512 字）。直接嵌入 2048 字会被**截断**，后半段信息全丢。所以
必须切到 400 字以内。切的时候按"段落→句号→逗号"优先级切，尽量不切断语义，相邻块
留 80 字重叠防止答案正好被切在边界。

**④ 每个 Point 存了什么**（`payload` = 附带数据）：

```python
{
  "text": "这段教材原文",       # 检索回来要给模型看的内容
  "source_id": 第几条教材段,    # 溯源
  "chunk_id": 这段的第几个切块,
  "source": "medical_book_zh"   # 来源标记（将来融合多源时区分内部/外部）
}
```

向量用 **COSINE 余弦相似度**度量（文本检索标准做法）。

**命令行开关**：`--limit N`（只灌前 N 条，验证用）、`--recreate`（清空重建）。

## 4. 检索验证（`kb_search.py` 新建）

实现了 **两段式检索**（生产级 RAG 标配）：

```
问题 → BGE 向量化 → Qdrant 向量召回 top-20（快、粗）
                  → BGE 重排 top-3（慢、精）→ 返回
```

为什么两段：向量召回快但不够准，先粗筛 20 条；再用更强的重排模型精排出最相关的
3 条。这比单纯向量检索准很多。

## 深入理解：CHUNK_SIZE / CHUNK_OVERLAP 为何这样设 & Qdrant 是什么

### CHUNK_SIZE=400：上有硬顶，下有底线

**硬顶 = BGE 的 512 token 上限。** bge-large-zh 一次最多吃 512 token，中文约「1 字 ≈ 1
token」。超过的部分**直接被截断丢掉**。所以一个 chunk 不能超过 ~512 字，400 留了安全余量
（标点、少数字符 >1 token，切分器也不会卡在精确 400）。

**底线 = 不能太小。** 为什么不切成 100 字？

| chunk 太大（如 800） | chunk 太小（如 100） |
|---|---|
| 超 BGE 上限被截断 | 语义被切碎 |
| 一块混多主题，向量被"平均"，检索不精准 | 一句话被拦腰斩断，答案散在好几块 |
| 塞给大模型时浪费上下文 | 检索回来的片段不完整 |

**400 是平衡点**：大到能装下一个完整概念/段落，小到向量还够"聚焦"、且稳在 512 以内。

### CHUNK_OVERLAP=80：防止答案被切在边界

**问题**：定长切分会把句子/答案正好切在两块交界处。若不重叠，问题落在 A 块、答案落在
B 块，两块都不完整，检索两边都捞不准。

**重叠的作用**：让相邻两块**共享一段内容**（这里 80 字），边界附近的文字同时出现在 A 和
B 里，保证任意 ~80 字片段至少在某一块里完整。

```
chunk A: …一线用药是 [钙通道阻滞剂和ACEI类药物]   ← 重叠的 80 字
chunk B: [钙通道阻滞剂和ACEI类药物] 的副作用包括…   ← 同一段也在这
```

**为什么是 80（=400 的 20%）**：业界经验值 10–20% 重叠。太少→边界问题没解决；太多→同样
文字反复嵌入存储，库膨胀、浪费算力、检索出重复结果。20% 是常用甜区。

> 这俩是 `config.py` 里**可调参数**（`.env` 能覆盖），最优值跟领域和嵌入模型有关。
> **懂背后的权衡比记住 400/80 更重要**——面试常考"为什么这么切"。

### Qdrant 是什么

**Qdrant（读 "quadrant"）是一个向量数据库**——专门存"向量"并按"相似度"搜索的数据库。

| | 普通数据库（MySQL） | 向量数据库（Qdrant） |
|---|---|---|
| 存什么 | 一行行结构化数据 | 一个个向量(embedding) + 原文 |
| 怎么查 | **精确匹配**：`WHERE 年龄=30` | **相似度**：找和这个向量最接近的 N 个 |
| 适合 | 订单、用户表 | "找语义最像这个问题的段落" ← RAG 要的 |

**为什么 RAG 必须用它**：有 5.9 万个 chunk，每次提问都拿问题向量挨个比太慢。向量库用专门
索引（HNSW 近似最近邻），**在几百万向量里也能毫秒级找出最相似的几个**。

**它存的每个单元叫 Point**：`向量(1024维) + payload(原文 + source_id + 来源标记…)`，
用 **COSINE 余弦相似度**度量。

**选型对比**：

| 选项 | 特点 |
|---|---|
| **Qdrant** ✅ | 本地落盘开发 + 单容器部署，Rust 写的快，LangChain 集成好 |
| FAISS | 是个库不是完整数据库，没有持久化/过滤 |
| Milvus | 企业级、能力强但部署重（要 etcd+minio） |
| Pinecone | 云服务，要付费、要联网 |
| Chroma | 最简单，但生产能力弱些 |

选 Qdrant 就因为它**开发期不用 Docker（本地落盘）、部署期一个容器搞定**，卡在"简单"与
"生产级"之间，还对得上 JD 点名的"向量数据库"。

> 做**混合检索**（dense 语义 + sparse 词面 + RRF 融合 + 重排）。届时 chunk 上限放宽，
> 本节的 512 限制只对 bge-large-zh 成立。
