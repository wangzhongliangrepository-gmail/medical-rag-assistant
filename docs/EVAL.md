# 检索评测：方法论、消融与一次静默退化的排查

本文记录医疗知识助手**检索层的评测体系**，以及评测过程中发现并修复的一个
**混合检索静默退化** bug。整体定位见根目录 [README](../README.md)、演进路线见
[设计文档索引](README.md)。

> 评测脚本集中在 [`eval/`](../eval/)：[`eval_retrieval.py`](../eval/eval_retrieval.py)（三方式指标）、
> [`run_chunk_eval.py`](../eval/run_chunk_eval.py)（切分 A/B 一键对比）、
> [`gen_eval_set.py`](../eval/gen_eval_set.py)（金标集反向生成）；金标数据在 [`eval/data/`](../eval/data/)。

---

## 1. 为什么不能用 EM/F1

医疗作答是**开放长文本**，没有唯一标准答案，逐词匹配的 EM/F1 失效。检索增强（RAG）
应用的质量可以拆成两段，分别评：

- **检索层**（本文重点）：金标 chunk 有没有被召回、排得够不够前 → 可量化、可复现。
- **答案层**：忠实度 / 完整性 / 是否带 `[编号]` 引用 → 需 LLM-as-judge（另见后续多跳评测）。

检索层评测的好处是**客观、快、可回归**，也正是它把下面那个肉眼看不见的 bug 照了出来。

## 2. 指标

对每个 `k`，跨所有问题求平均：

| 指标 | 含义 | 在乎排名 |
|------|------|----------|
| **Hit@k** | 前 k 条里**至少**命中一个金标的问题占比 | ❌ |
| **Recall@k** | 前 k 条里命中的金标数 / 该题金标总数 | ❌ |
| **MRR@k** | 第一个命中金标的排名倒数（命中第 1 名=1.0，第 2 名=0.5…） | ✅ |

Recall 回答「**答案捞回来了吗**」，MRR 回答「**排得够靠前吗**」。RAG 里两者都重要：召回是
前提（没召回，LLM 只能编），MRR 高则最相关证据排在最前、喂给 LLM 的上下文质量最高也最省 token。

## 3. 评测集设计

**反向生成**（[`gen_eval_set.py`](../eval/gen_eval_set.py)）：从库里挑一个 chunk → 让 LLM 生成
「这段能回答的问题」→ 这段天然就是该问题的金标。批量生成后**人工审核**。

- 金标用 `(source_id, chunk_id)` 唯一标识：`source_id` = 教材原始段落号，`chunk_id` = 切分后第几块。
- 当前草稿集 50 题、每题 1 个金标（**单跳**）。

> **已知局限**（评测时一并报告，避免过度解读）：
> - **n 小**：草稿 50 题，切分子集实验实际只用到 16 题（见 §4），每题权重 1/16 ≈ 0.0625，
>   任何 ±0.062 的差异本质都只是「一道题翻盘」，属方向性信号、非统计显著。
> - **单跳、单金标**：测不了桥接多跳；且一题可能有别的 chunk 也能答却未标注 → **真实 recall 被低估**。
> - **反向生成偏乐观**：问题由 chunk 倒推，措辞贴近原文，比真实用户提问更易召回 → 绝对分偏高。

## 4. 切分策略 A/B + 逐层消融

[`run_chunk_eval.py`](../eval/run_chunk_eval.py) 做一个**自给自足、与线上库隔离**的子集实验：取前
**3000 个源段落**（切分**之前**的教材原始段落），分别用 `recursive`（递归字符切分）和
`structure`（按【小节】标题结构切分）各灌一个独立小库，再对**同一批**金标（限定金标
`source_id < 3000`，共 16 题）评测。`--max-source 3000` 同时约束候选池与题目，保证两种
切分**公平对比**。

每个库都跑三种检索方式，逐层加码以量化各层增益：

1. `dense`：纯 bge-m3 稠密语义检索；
2. `hybrid(RRF)`：dense + sparse(BM25) 双路 Qdrant 原生 RRF 融合；
3. `hybrid+rerank`：融合候选再过 BGE reranker 精排（= 线上完整路径）。

**切分结论（线上路径 `hybrid+rerank`，修复 sparse 后）：**

| k | recursive R@k | structure R@k | ΔR | recursive MRR | structure MRR | ΔMRR |
|---|---|---|---|---|---|---|
| 1 | 0.688 | 0.688 | 0 | 0.688 | 0.688 | 0 |
| 3 | 0.812 | 0.812 | 0 | 0.729 | 0.750 | +0.021 |
| 5 | 0.812 | **0.875** | +0.062 | 0.729 | **0.766** | +0.036 |
| 10| 0.812 | **0.875** | +0.062 | 0.729 | **0.766** | +0.036 |

结构切分在线上路径上 **k=1/3 持平、k=5/10 略优，MRR 在 k≥3 全程小升，无任何回退** → **弱正向，
可采纳**。但 source 级 recall **照不出结构切分的核心收益**（不把「禁忌/不良反应」从中间截断 →
答案更完整），那属答案层增益，需 LLM-judge 才量得到——这里不夸大。

## 5. 评测照出的静默退化：BM25 中文分词

这是本评测体系最有价值的一次产出——**一个不跑评测就永远发现不了的 bug**。

### 5.1 异常信号

修复前的对比表里，`dense` 与 `hybrid(RRF)` **每个 k 的指标完全相同**：

| k | dense R@k | hybrid(RRF) R@k | Δ |
|---|---|---|---|
| 1 | 0.438 | 0.438 | **0** |
| 3 | 0.688 | 0.688 | **0** |
| 5 | 0.812 | 0.812 | **0** |
| 10| 0.875 | 0.875 | **0** |

两条**不同的检索路径**（一条只走 dense，一条 dense+sparse 融合）不可能给出**逐条完全一致**
的结果。唯一的解释：**sparse 那一路返回了空，RRF 在「dense 结果 + 空」上退化成纯 dense**。
混合检索一直在「正常」返回结果（因为 dense 在干活），从外部完全看不出问题——**是评测里这个
恒等信号把它逮住的**。

### 5.2 根因定位

逐层诊断（集合 schema → 文档侧向量 → 查询侧向量 → 单路召回）：

- 集合 schema 正常：sparse 向量已定义、IDF modifier 已开。
- 文档侧正常：样本点确有 sparse 向量（26 个非零维）。
- **查询侧异常**：查询「高血压用药注意事项」的 sparse 向量**只有 1 个非零维**，sparse 单路召回 **0 条**。

进一步用加/不加空格对照，锁定分词器行为：

| 输入 | sparse 非零维度数 |
|------|------------------|
| `高血压用药注意事项` | **1** |
| `高血压 用药 注意 事项`（手动加空格） | 4 |
| `阿司匹林` | **1** |
| `糖尿病,高血压;用药`（带标点） | 3 |

**根因**：FastEmbed 的 `Qdrant/bm25` 分词器只按**空白/标点**切词，**不切连续中文**——整段无标点的
中文被压成**一个 token**。文档侧因标点多被切成一堆「整句/短语」token（故有 26 维），查询侧短句无
内部标点 → 压成 1 个 token → 与任何文档 token 都不精确相等 → BM25 召回 0 → **混合检索静默退化为
纯 dense**。

### 5.3 修复

在 [`sparse.py`](../sparse.py) 引入 **jieba 中文分词**，**文档侧与查询侧用同一套切法**（先切词、空格
拼接再交给 BM25），保证 term 对齐。dense（bge-m3）完全不变，故无需重算——用
[`reindex_sparse.py`](../reindex_sparse.py) 经 Qdrant `update_vectors` **只增量覆盖 sparse 命名向量**
（payload 与 dense 原封不动），IDF 由库侧按新全集重新统计。

### 5.4 修复验证

复测后 `hybrid(RRF)` 不再等于 `dense`，sparse 开始实质贡献（structure 库）：

| k | dense R@k | hybrid R@k | ΔR | dense MRR | hybrid MRR | ΔMRR |
|---|---|---|---|---|---|---|
| 1 | 0.438 | **0.500** | +0.062 | 0.438 | **0.500** | +0.062 |
| 3 | 0.688 | **0.750** | +0.062 | 0.552 | **0.615** | +0.063 |
| 5 | 0.812 | 0.812 | 0 | 0.580 | **0.627** | +0.047 |
| 10| 0.875 | 0.875 | 0 | 0.591 | **0.634** | +0.043 |

机制层面 **sparse 从「0 贡献」恢复到「有贡献」**（这是确定性结论，与样本量无关）；数值层面 Recall@1/3
与 MRR 全程小升（受 n=16 限制，作方向性看）。至此「dense → +sparse → +rerank」逐层加码的阶梯才真正成立。

### 5.5 一句话复盘

> 评测发现 `hybrid` 与纯 `dense` 指标完全一致 → 据此判定混合检索静默退化 → 定位到 FastEmbed BM25
> 不分中文、sparse 向量近乎为空 → 引入 jieba 分词、增量重建 sparse 索引 → 复测验证 sparse 贡献恢复。
> **价值不在「修了个 bug」，而在「评测抓住了一个肉眼不可见的静默故障」。**

## 6. 复现

```bash
# 评测脚本都在 eval/，从仓库根运行
# 切分 A/B + 逐层消融（首次会建两个 3000 段子集；已建过加 --skip-ingest）
python eval/run_chunk_eval.py
python eval/run_chunk_eval.py --skip-ingest

# 单库三方式评测
python eval/eval_retrieval.py --gold eval/data/eval_set_draft.json --match source --k 1 3 5 10

# sparse 修复后重建索引（只更新 sparse，不动 dense）
QDRANT_PATH=./qdrant_db QDRANT_COLLECTION=medical_kb python reindex_sparse.py
```

> 前置：Xinference 开着（dense 向量化 + 重排走 GPU）；sparse/BM25 与 jieba 跑 CPU。

## 7. 后续

- **答案层 LLM-judge**：忠实度 / 完整性 / 引用规范，量化结构切分「答案更完整」的真实收益。
- **多跳桥接评测**：金标改为「一对有依赖关系的 chunk」，用 `use_reflect` 开关做 A/B 消融，
  量化反思回路对桥接多跳的增益。
- **扩集 + 人工审**：把 16/50 的 n 提上去，压住「一题翻盘」的噪声。
