# 学习串讲：Planning（拆解问题）

> 医疗助手的 `plan` 节点：把复合问题拆成多方面子问题分别检索。配合 `med_nodes.py` 阅读。

## 一、这个节点干什么

代码（`med_nodes.py` 第 89-108 行）：

```python
_PLAN_PROMPT = """你是医疗问答规划器。把下面的问题拆成 1-3 个可独立检索的子问题，
覆盖问题的不同方面（如疾病机理、药物选择、副作用、用药注意事项等）。
若问题本身很单一，只输出一个子问题（即原问题）。
问题：{question}"""

class SubQuestions(BaseModel):
    questions: list[str]

def plan(state, config):
    question = state.get("standalone_question") or state["question"]
    structured = _llm(config).with_structured_output(SubQuestions, method="json_mode")
    result = structured.invoke([...])
    subs = result.questions or [question]
    return {"plan_questions": subs, "sub_questions": subs}
```

干的事：**让 LLM 把一个复合问题拆成 1-3 个能各自独立检索的子问题。**

## 二、实际拆解例子

**例 1：复合问题 → 拆成多方面**
```
输入："二甲双胍的副作用和禁忌症"
拆成：["二甲双胍的副作用", "二甲双胍的禁忌症"]
```

**例 2：多方面问题**
```
输入："高血压怎么治，平时生活要注意什么"
拆成：["高血压的一线治疗药物", "高血压患者的日常生活注意事项"]
```

**例 3：单一问题 → 不拆（关键）**
```
输入："二甲双胍的副作用有哪些"
拆成：["二甲双胍的副作用有哪些"]   ← 只有 1 个，等于没拆
```

**例 4：复杂多方面**
```
输入："糖尿病人能喝酒吗，对血糖有什么影响，有什么风险"
拆成：["饮酒对糖尿病患者血糖的影响",
       "糖尿病患者饮酒的健康风险",
       "糖尿病患者饮酒的注意事项"]
```

## 三、为什么要拆（Planning 的灵魂）

**因为检索是「按子问题分别去捞证据」的。** 下游 `retrieve_internal` 遍历每个子问题各自检索 top-k 再累积。

以例 1「二甲双胍的副作用和禁忌症」**若不拆**：拿整句去检索，向量检索可能主要召回「副作用」段落，「禁忌症」被挤掉 → 答案只讲副作用、禁忌缺失。拆开后两方面证据都进池，答案才完整。

> 一句话：**Planning 解决「单次检索覆盖不全」——复合问题拆成多方面，各自检索，证据更全面。**

## 四、关键设计点（面试考点）

1. **平行拆解（parallel decomposition）**：子问题互相独立、可同时检索。区别于「桥接/多跳型」（后跳依赖前跳答案）。
2. **结构化输出，不用正则**：`with_structured_output(SubQuestions, method="json_mode")` + Pydantic，强制返回合法 `{"questions": [...]}`，绝不用正则抠自由文本。
3. **故意不过度拆解**：prompt 明说单一问题只输出一个子问题。过度拆解会打散语义、引入噪声、白花检索。
4. **兜底（fallback）**：`subs = result.questions or [question]`，LLM 返回空时用原问题兜底，流程不断。
5. **衔接记忆**：拆的是 `standalone_question`（指代消解后的），不是原始 `question`，所以「那它的禁忌呢」已先被改成「二甲双胍的禁忌」再拆，子问题里不含悬空指代。

## 五、一个诚实的局限（讲出来加分）

**平行拆解搞不定「桥接型」问题。** 例：
```
"治疗高血压的一线药，它的副作用是什么"
```
要先查「一线药是谁」（如 ACEI），才能查「ACEI 的副作用」。平行拆会拆出悬空的「那个药的副作用」，检索全是噪声。

解决靠**链式精化**（先检索第一跳、把答案代入第二跳再检索），见 `docs/P2_5_DESIGN.md`；当前 `plan` 是平行版。面试被问「拆解有什么局限」，这是满分答案——能说出局限 + 知道怎么解。

## 六、面试问题清单（带答题要点）

1. 为什么要拆解问题，不拆直接检索不行吗？

   **因为检索是「按子问题分别去检索证据」。** 后面的`retrieve_internal` 遍历每个子问题各自检索 top-k 再累积。

   **若不拆**：拿整句去检索，向量检索可能主要召回「副作用」段落，「禁忌症」被挤掉 → 答案只讲副作用、禁忌缺失。拆开后两方面证据都进池，答案才完整。**Planning 解决「单次检索覆盖不全」——复合问题拆成多方面，各自检索，证据更全面。**

2. 平行拆解 vs 多跳/桥接拆解，区别？你用哪种？ 

   平行=子问题独立可并行；桥接=后跳依赖前跳。本项目平行；桥接需链式精化。

3. 拆解一定更好吗？

    不一定，过度拆解打散语义、增噪，所以单一问题不拆。 因此在拆解的prompt 中去约束对于简单，单一问题只输出一个子问题。

4. 怎么保证 LLM 输出可解析？→ 结构化输出 + Pydantic，不用正则。

5. 为什么限制 1-3 个？

   够覆盖医疗复合问题，又不过度拆、不爆检索量。

6. 拆解失败/返回空怎么办？

   LLM 返回空时用原问题兜底，流程不断。

7. 多个子问题分别检索，证据会重复爆炸吗？

   `retrieve_internal` 用 `(source_id, chunk_id)` 去重，且每子问题只取 top-k。

8. 拆解用什么模型？能换吗？→ `_llm(config)`，按请求 flash/pro 动态选。

## 深入理解：CHUNK_SIZE / CHUNK_OVERLAP 为何这样设 & Qdrant 是什么

### CHUNK_SIZE=400：上有硬顶，下有底线

**硬顶 = BGE 的 512 token 上限。** bge-large-zh 一次最多吃 512 token，中文约「1 字 ≈ 1
token」。超过的部分**直接被截断丢掉**。所以一个 chunk 不能超过 ~512 字，400 留了安全余量
（标点、少数字符 >1 token，切分器也不会卡在精确 400）。

**底线 = 不能太小。** 为什么不切成 100 字？

| chunk 太大（如 800）                   | chunk 太小（如 100）             |
| -------------------------------------- | -------------------------------- |
| 超 BGE 上限被截断                      | 语义被切碎                       |
| 一块混多主题，向量被"平均"，检索不精准 | 一句话被拦腰斩断，答案散在好几块 |
| 塞给大模型时浪费上下文                 | 检索回来的片段不完整             |

**400 是平衡点**：大到能装下一个完整概念/段落，小到向量还够"聚焦"、且稳在 512 以内。

### CHUNK_OVERLAP=80：防止答案被切在边界

**问题**：定长切分会把句子/答案正好切在两块交界处。若不重叠，问题落在 A 块、答案落在
B 块，两块都不完整，检索两边都捞不准。

**重叠的作用**：让相邻两块**共享一段内容**（这里 80 字），边界附近的文字同时出现在 A 和
B 里，保证任意 ~80 字片段至少在某一块里完整。

```
chunk A: …一线用药是 [钙通道阻滞剂和ACEI类药物]   ← 重叠的 80 字
chunk B: [钙通道阻滞剂和ACEI类药物] 的副作用包括…   ← 同一段也在这
```

**为什么是 80（=400 的 20%）**：业界经验值 10–20% 重叠。太少→边界问题没解决；太多→同样
文字反复嵌入存储，库膨胀、浪费算力、检索出重复结果。20% 是常用甜区。

> 这俩是 `config.py` 里**可调参数**（`.env` 能覆盖），最优值跟领域和嵌入模型有关。
> **懂背后的权衡比记住 400/80 更重要**——面试常考"为什么这么切"。

### Qdrant 是什么

**Qdrant（读 "quadrant"）是一个向量数据库**——专门存"向量"并按"相似度"搜索的数据库。

|        | 普通数据库（MySQL）           | 向量数据库（Qdrant）                  |
| ------ | ----------------------------- | ------------------------------------- |
| 存什么 | 一行行结构化数据              | 一个个向量(embedding) + 原文          |
| 怎么查 | **精确匹配**：`WHERE 年龄=30` | **相似度**：找和这个向量最接近的 N 个 |
| 适合   | 订单、用户表                  | "找语义最像这个问题的段落" ← RAG 要的 |

**为什么 RAG 必须用它**：有 5.9 万个 chunk，每次提问都拿问题向量挨个比太慢。向量库用专门
索引（HNSW 近似最近邻），**在几百万向量里也能毫秒级找出最相似的几个**。

**它存的每个单元叫 Point**：`向量(1024维) + payload(原文 + source_id + 来源标记…)`，
用 **COSINE 余弦相似度**度量。

**选型对比**：

| 选项         | 特点                                                     |
| ------------ | -------------------------------------------------------- |
| **Qdrant** ✅ | 本地落盘开发 + 单容器部署，Rust 写的快，LangChain 集成好 |
| FAISS        | 是个库不是完整数据库，没有持久化/过滤                    |
| Milvus       | 企业级、能力强但部署重（要 etcd+minio）                  |
| Pinecone     | 云服务，要付费、要联网                                   |
| Chroma       | 最简单，但生产能力弱些                                   |

> 我选 Qdrant 是因为项目是中等规模的医疗 RAG(约 5 万段),Qdrant 单机性能足够、且部署轻——一个容器或本地落盘就能跑,混合检索(dense+sparse 命名向量 + 原生 RRF 融合)API 也直观,正好支撑我的混合检索方案。Milvus 更适合十亿级、需要存算分离弹性扩展的超大规模场景,但它要                                               
>   ▎ etcd/MinIO/消息队列一堆组件,对我这个量级是过度设计、运维负担不划算。如果未来数据涨到十亿级或要多租户大规模,会考虑迁 Milvus/Zilliz。"

Milvus:为**十亿级+**向量、超高吞吐设计,存算分离能独立扩 query/data 节点,水平扩展能力更强。大厂海量场景的常见选择。                                                                                                                                                                                              
  - Qdrant:单机性能很强(Rust + 高效 HNSW),千万级、甚至到亿级也能扛;再往上的超大规模分布式不如 Milvus 成熟。                                                                                                                                                                                                         
  - 你项目才 5 万段,两者性能都绰绰有余,这个维度对你不构成区别。
