# P2 设计：+Planning（复合问诊拆方面）

## 目标

给医疗助手加 Agent 的 **Planning 支柱**：一次问诊常跨多个方面（机理 / 用药 / 副作用 / 禁忌…），
单次检索覆盖不全 → 先把复合问题**拆成 1-3 个可独立检索的子问题**，分别检索再汇总。

## 为什么是「平行拆解」而非「链式精化」

医疗问诊里的复合问题，绝大多数是**并列的多个方面**（「二甲双胍的副作用**和**禁忌」=
两个独立可检索的方面），彼此不依赖 → **平行拆解 + 各自检索 + 合并去重**即可，简单稳。

链式精化（后一跳依赖前一跳的答案，如「先查它属于哪类药 → 再查该类药的一线推荐」）属于
**桥接型**，复杂度高、收益场景窄，**暂未实现**（列入路线图）。

## 实现（`med_nodes.py: plan / retrieve_internal`）

```
question → plan → retrieve_internal（对每个子问题检索，去重累积）→ fuse → answer
```

| 环节 | 实现 | 关键点 |
|------|------|--------|
| 拆解 | `plan` 节点，结构化输出 `SubQuestions{questions: list[str]}` | DeepSeek `json_mode`，不靠正则抠 |
| 约束 | prompt 限 **1-3 个**子问题；问题本身单一就只返回 1 个（即原问题） | 防过度拆解徒增检索/延迟 |
| 检索 | `retrieve_internal` 对每个子问题各跑一次混合检索 | 结果按 `(source_id, chunk_id)` 去重累积 |

退化保护：`subs = result.questions or [question]`——LLM 给空也至少检索原问题，不会断链。

## 关键设计取舍

- **结构化输出而非解析自由文本**：DeepSeek 支持 `json_mode`，直接拿 `list[str]`，避免脆弱正则
  （CLAUDE.md 硬约束）。
- **拆解只在 `standalone_question` 上做**：[P5](P5_DESIGN.md) 接入后，`plan` 读的是指代消解后的
  自包含问题，所以「那它的禁忌呢」也能被正确拆解。
- **去重在检索层**：不同子问题可能召回同一段教材，按来源 id 去重，避免证据池冗余、重排被灌水。
- **`plan_questions` 与 `sub_questions` 双字段**：前者留作前端展示「理解为这几个方面」，
  后者作检索队列，职责分开。

## 验证

复合问题「高血压一线药有哪些、各自的副作用」→ `plan` 拆为「高血压一线降压药种类」+
「各类一线降压药的副作用」两个子问题，分别召回后合并 → 答案两个方面都覆盖、各带 `[编号]`。✓

- 子问题数量目前由 LLM 自判（1-3），可加「问题复杂度 → 动态上限」的更细控制。
- 桥接型链式精化（依赖前一跳答案的多跳检索）→ 路线图。
